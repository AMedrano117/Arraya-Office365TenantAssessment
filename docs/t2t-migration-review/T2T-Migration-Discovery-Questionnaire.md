# T2T Migration Discovery Questionnaire

Review date: 2026-11-10
Related documents: [coverage](T2T-Migration-Assessment-Coverage.md), [backlog](T2T-Migration-Assessment-Backlog.md), [application identity mapping template](../templates/T2T-Application-Identity-Mapping-Template.csv)

## Purpose and rules of use

This questionnaire holds the questions that tenant collection cannot answer reliably. It complements two existing documents and does not replace them:

- `docs/templates/Microsoft 365 Tenant to Tenant Questionnaire.md` (inventory-style questions that the assessment partly auto-answers).
- The Presales scope questionnaire generated by `Export-PresalesMigrationScopeQuestionnaireMarkdown.ps1` (scope and tooling decisions keyed by `DecisionKey`).

Rules:

- Ask each question for the source tenant, the destination tenant, or both, as marked. Record which tenant an answer describes.
- Audience values: **Customer** (business, IT, security, legal, or compliance owner), **Vendor** (application, migration-tool, gateway, or service vendor), **Customer and vendor**.
- An answer is evidence only when it names who confirmed it and when. Until then the related item stays "Needs Input".
- Do not pre-fill owners, dates, target states, or commitments.
- "Feeds" shows the existing or proposed decision key or register. Keys marked with an asterisk are proposed in backlog item P1-12 and do not exist yet.
- Vendor behavior changes. Record the vendor document or ticket that supports each vendor answer.
- The coverage matrix refers to sections of this document by code: Q-ID (1 Identity), Q-LIC (2 Licensing), Q-EX (3 Exchange), Q-MF (4 Mail flow), Q-GRP (5 Groups), Q-SSO (6 SSO and applications), Q-TEAMS (7 Teams), Q-SP (8 SharePoint and OneDrive), Q-FS (9 File servers), Q-EP (10 Endpoints), Q-SEC (11 Security and compliance), Q-UX (12 User experience), Q-SUP (13 Support), Q-GOV (14 Governance).

Risk cases to record in the "Risk cases" column:

1. NameID equals the current email or UPN.
2. Email is the vendor's immutable account key.

9. The source domain cannot be removed until the application is remapped.

### Transitional application-specific NameID

Changing a user's UPN or primary SMTP address does not, by itself, change the account safely in a SaaS application. Where the application keys accounts on the old email-style identifier and cannot rename or bulk-map them in time, one controlled option is to keep sending the old value to that one application while the directory identity changes:

- New Entra UPN: `jdoe@newbrand.example`
- Temporary application-specific SAML NameID: `jdoe@source-domain.example`

This is a transitional design for a single application, not a general recommendation.
