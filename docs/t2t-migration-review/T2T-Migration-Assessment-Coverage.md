## How this review was done

- Static review of the collectors, normalization, findings, and report code, tracing each requirement from collection to customer-facing output. A field with a matching name was not counted as coverage unless it reaches a report.
- Offline reproduction of suspected defects. Production functions were loaded with the same AST-extraction pattern used by `tests/unit/MigrationScopeReconciliation.Tests.ps1` and run against synthetic fixtures and mocked Microsoft Graph payloads. Results are listed as R1 to R10 in section 6.
- No tenant was contacted. No customer export was opened. All fixture values use reserved `.example` domains.
- Microsoft behavior that drives a finding was checked against Microsoft Learn on 2026-11-10 and is listed in the appendix. Third-party tool behavior was not verified and is marked as such.

Reference scenario used to judge adequacy: a tenant-to-tenant migration with a short, customer-specific legal deadline for the first transition (the review brief called it "Day 1"), a cloud-only source tenant that still has an on-premises Active Directory with domain-joined devices, a hybrid destination tenant (accounts created in destination AD and synchronized by Microsoft Entra Connect), new UPN and primary SMTP domains, third-party mailbox migration continuing after that deadline, B2B guests replaced by destination member identities, a SharePoint tenant rename with a new fallback domain, SAML applications that must keep existing application profiles, deferred endpoint migration, external mail-security gateways, and unresolved destination licensing.

### Design correction after the review

The reference scenario has a deadline. A tenant-to-tenant migration in general does not. Engagements may be phased, coexistence-based, wave-based, a single cutover, identity-first, messaging-first, or have no single business cutover date. The reusable assessment therefore collects and interprets evidence without assuming any of these models: it defines no "Day 1", no fixed phases, and no required cutover. Milestones, waves, cutover dates, coexistence requirements, and acceptance criteria are engagement inputs that belong in project decisions, questionnaires, wave plans, and runbooks. The "Migration impact" column in section 4 describes the consequence of a gap in neutral terms. Where this document mentions a deadline it is describing the reference scenario only.

Status of the corrections proposed here is tracked in [T2T-P0-Implementation-Status.md](T2T-P0-Implementation-Status.md). Sections 6 and 7 describe the code as reviewed at commit `66f48a8`, before those corrections.

## 1. Executive summary

The repository is a strong Exchange and collaboration sizing tool with a well-designed decision register. It is not yet adequate to plan the reference scenario, for three reasons.

1. Several migration statements are produced from missing data. Ten defects were reproduced offline (section 6). The most serious: every tenant is flagged as having AD Connect synchronization and Exchange hybrid "Configured"; an unknown sync state is reported as "Cloud-only identity model, Ready"; Multi-Geo is never detected; items with no collected data are scored "Ready" and then dropped from the cutover checklist; mailboxes on non-litigation holds are counted as not on hold.
2. The profile named for this work collects the least identity evidence. `TenantToTenantMigration` disables Entra groups, authentication and enterprise applications, Conditional Access, MFA, administrators, Microsoft 365 Groups, devices, and Purview collection, and its workbook and HTML report omit the planning registers that the Presales profile produces. Selecting it together with another profile restores collection but silently turns off the tenant-to-tenant shaping. No single run produces both the evidence and the migration registers.
3. The assessment models one tenant with no role. There is no source-versus-destination concept, no second-snapshot comparison, and therefore no collision analysis, no guest-to-member mapping, and no destination hybrid-identity evidence. SAML NameID, claims, SCIM matching, and application assignments are not collected at all.

What is adequate today: mailbox inventory, sizing, archive and inactive-mailbox handling, delegate and calendar-permission inventories, SMTP relay evidence states, SharePoint and OneDrive inventories with activity, Microsoft 365 Group and Teams reconciliation, the MigrationWiz license model, and the `DecisionKey` register that keeps discovered evidence apart from customer confirmation.

Seven corrections are classified P0 and are narrowly scoped. None was implemented in this review. The proposed change set is in the [backlog](T2T-Migration-Assessment-Backlog.md).

## 3. Current strengths

- Evidence is kept apart from decisions. `Update-MigrationPlanningRegisters` writes `DiscoveredValue`, `EvidenceSource`, `CustomerConfirmedValue`, `DecisionOwner`, `DueDate`, and `Status` separately, never fills owners or dates, and states "Not discoverable from the source-only assessment" for destination checks.
- Section approvals cannot confirm object rows. Only an exact object `DecisionKey` with an approved status changes a row, and an unconfirmed exclusion never shrinks scope.
- Missing evidence is handled correctly in the newer code paths: Teams enrichment (`ChannelInventoryStatus`, `MemberInventoryStatus`), group mailbox statistics, mailbox license evidence, SMTP AUTH and relay connector evidence states, delegate collection states, and enterprise application signal states (`OwnerSignalState`, `RedirectUriSignalState`, `ActivitySignalState`).
- Mailbox migration sizing is thorough: primary, deleted-item, archive, and archive deleted-item sizes, inactive mailbox restore prerequisites, oversize thresholds, and a license model that reports unit baskets without inventing a recommendation or price.
- Delegation is inventoried at the row level: Full Access, Send As, Send on Behalf, and per-folder calendar permissions with sharing flags.
- SharePoint, OneDrive, Microsoft 365 Group, and Teams storage is reconciled once, with channel-site flags and activity state.
- Tooling notes are explicit that vendor terms change (`migration-tooling-options.json` review policy; Teams private chat note).
- Collector failures are classified (`Passed`, `Degraded`, `Failed`) and required collectors gate the run.
- Read-only collection, tenant-mismatch guard, and credential metadata without secret values.

## 5. Material gaps

1. **No tenant role and no source-to-destination comparison.** Every register is source-only (`ConflictStatus` is fixed at "Not evaluated against destination"). Collisions on UPN, SMTP, proxy address, mail nickname, and display name, guest-to-member mapping, and proposed-domain conflicts cannot be found. The `Compare` action compares posture metrics of one tenant over time, not two tenants.
2. **The tenant-to-tenant profile does not collect identity, application, group, device, or compliance evidence** (collection plan lines 652 to 673), and merged selections disable its shaping. The reverse also holds: Full Access, Send As, and calendar-permission enumeration run only under the `TenantToTenantCutover` scope policy (`Get-ArrayaCollectionDepthPolicy`, legacy script lines 3142 to 3143 and 3163 to 3164), so every other profile and every merged selection omits delegates. The same policy turns off Microsoft 365 Group mailbox statistics and full SharePoint detail for the tenant-to-tenant profile (lines 3165 to 3166). Two separate runs are needed today to get both halves.
3. **SAML and SCIM continuity evidence is absent.** NameID source and format, claims and transformations, user and group assignments, signing certificates on service principals, provisioning jobs, and matching attributes are not collected. There is no application identity mapping worksheet.
4. **Hybrid identity evidence stops at tenant-level flags.** Sync client type, server identity, staging mode, and health are never populated. On-premises filtering and rules are not requested from the customer.
5. **No calendar or meeting evidence and no report language that separates copied items from operational continuity.**
6. **No group disposition register.** Group data exists in three collectors but is never combined, cross-referenced to its consumers, or given a disposition.
7. **No milestone or sequencing model.** Nothing links an item to an engagement-defined milestone, wave, or sequencing dependency, or separates a customer decision from a vendor dependency.
8. **Licensing readiness is not modeled** beyond one bundled destination-capacity decision.
9. **Tenant rename readiness is not evaluated** although site counts are collected, and Multi-Geo detection is broken.
10. **Endpoint and file-server discovery are outside the tenant collector** and have no import contract or questionnaire. The AD workflow exists but is not linked.

## 8. Findings and report semantics

| Criterion | Assessment |
| --- | --- |
| Evidence-based | Mixed. Registers and newer evidence-state fields are evidence-based. The older readiness rows and the tenant-to-tenant questionnaire are count-based without collection state (R3 to R8). |
| Avoid unsupported claims | Not met in the cases listed in section 6. |
| Separate observation, risk, recommendation, and customer decision | Partly. The Presales registers separate discovered values from customer-confirmed values. `MigrationReadiness`, `MigrationComplexityFlags`, and `CutoverPrepSummary` mix them in `Status`, `Notes`, and `MigrationAction`. |
| Missing data is not a deficiency | Met in Teams, group mailbox, SMTP, delegate, and application-signal logic. Not met in the readiness rows, where missing data is treated as a pass. |
| Blockers versus later optimization | Not met. `Blocker` means "blocks a firm quote". Nothing expresses a dependency of an engagement-defined milestone. |
| Source versus destination scope | Partly. Destination checks are labeled as not discoverable. There is no tenant-role attribute on evidence rows. |
| Email-domain change versus Windows sign-in change | Not addressed. UPN and SMTP targets exist per user; device sign-in, cached credentials, and domain membership are not represented. |
| Migrated content versus operational continuity | Not addressed for calendars, Teams chat, guest history, and SSO application profiles. |
| Licensing dependencies without assuming entitlement | Partly. The BitTitan model is careful. The questionnaire infers usage from service plans, and "Target licensing readiness" reports source utilization. |
| Customer-friendly and technically specific | Generally good. The vocabulary of `Status` differs between tables (Ready, Review, Blocker, Needs Data, Info, Condition, Complete, Provisional). |

### Proposed migration-readiness output model

Extend the existing registers instead of adding a parallel model. `MigrationScopeDecisions` and the readiness rows keep `DecisionKey`, `Status`, `CustomerConfirmedValue`, `DecisionOwner`, `DueDate`, and `Notes`. Add these attributes to every readiness, flag, and decision row:

| Attribute | Values | Rule |
| --- | --- | --- |
| `ItemType` | Confirmed current state; Target-state decision; Requirement; Blocker; Risk; Evidence gap; Customer question; Vendor question; Recommended validation | Exactly one. An evidence gap is never a risk or a pass. |
| `Milestone` | Free text supplied by the engagement (a wave, stage, or cutover name); empty by default | Never generated by the tool. The assessment defines no fixed phases, no "Day 1", and no required cutover. "Out of scope" is a separate customer decision. |
| `Workstream` | Identity; Messaging; Collaboration; Applications; Endpoints; Security and compliance; User experience; Governance | Fixed per rule. |
| `TenantRole` | Source; Destination; Both; Not applicable | Set from the snapshot role once P1-05 exists; "Source" until then. |
| `EvidenceClass` | Collected; Inferred; Customer-confirmed; Vendor-confirmed; Not collected; Not collectible | "Collected" requires a successful collector state, not a non-empty table. |
| `EvidenceSource` | Dataset and field, or questionnaire id | Required when `EvidenceClass` is Collected or Inferred. |
| `DependencyType` | None; Customer decision; Vendor dependency; Blocked by another item | With `BlockedBy` holding a `DecisionKey`. |
| `OwnerState` | Assigned; Owner not assigned | Derived from `DecisionOwner`; never defaulted. |
| `DateState` | Confirmed; Date not confirmed | Derived from `DueDate`; never defaulted. |

Status values for evidence rows should be reduced to one vocabulary: `Confirmed`, `Review`, `Blocker`, `Needs Data`, `Needs Input`, `Not applicable`. "Ready" should be reserved for a state that was positively observed, and a "Ready" row may be hidden only when `EvidenceClass` is Collected.

Owners, dates, target states, and customer commitments must remain empty until entered and confirmed. The existing merge rules already enforce this and should be kept.
